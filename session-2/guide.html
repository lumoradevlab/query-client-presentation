نقشه‌ی جلسه‌ی ۲ — قبل از هر چیز این را بخوانید

جلسه‌ی ۲ از ۳ · The engine · حدود ۶۵ دقیقه · ۲۹ اسلاید · باز کردن اسلایدها

کار این جلسه: هفته‌ی پیش کلاس پر از سؤال‌های فنی بود: engine چطور کار می‌کند، این همه request، payload، و query state کنار UI state. این جلسه دقیقاً به همان‌ها جواب می‌دهد، با کد واقعی ComposeCleanArch. این بار جواب «جلسه‌ی بعد» نیست؛ امروز همان جلسه است.

لحن: مخاطب مهندس است و به ادعا اعتماد نمی‌کند. هر ادعا را با کد یا test نشان دهید، و هر جا engine کاری را نمی‌کند (اسلاید ۲۶) صادقانه بگویید. «نمی‌دانم، چک می‌کنم» از یک حدس غلط بهتر است.

جمله‌ی اصلی (اسلاید ۷ می‌گویید، اسلاید ۲۷ تکرار می‌کنید):

«جعبه فقط وقتی به سرور می‌رود که دلیل داشته باشد: خالی است، stale است، یا می‌دانیم عوض شده. هر چیز دیگری صفر request است.»

اسلاید ۴ · حدود ۳ دقیقه

کجای مسیر هستیم: جواب سؤال اول، «engine چطور کار می‌کند». این اسلاید فهرست کل جلسه است: هر فیلد بعداً یک اسلاید خودش را دارد.

ایده (برای خودتان)

کل رفتار جعبه از همین چند فیلد درمی‌آید (کد واقعی در QueryEntry.kt، خطوط ۶۳ تا ۸۶):

سه فیلد دیگر هم هست که روی اسلاید نیامده: _isManualRefetch (برای spinner ی pull-to-refresh، اسلاید ۲۳)، cleanupJob (تایمر cacheTime، اسلاید ۹) و sourceJob (اتصال به Room در useCachedQuery، جلسه‌ی ۳).

چرا Atomic؟ سه thread به این فیلدها دست می‌زنند: main (composition، observe/unobserve)، IO (بدنه‌ی fetch در scope ی QueryClient) و حلقه‌ی polling. var ساده یعنی race. همان استدلال هفته‌ی پیش برای ConcurrentHashMap، این بار داخل جعبه.

  2. → کارت WHY ATOMIC، و کل کد روشن.
«کل engine همین شش فیلد است. هر کدام یک اسلاید امروز است. اگر وسط جلسه گم شدید، به این اسلاید برگردید.»

اگر پرسیدند

  • «چرا StateFlow و نه LiveData یا SharedFlow؟» StateFlow همیشه یک مقدار فعلی دارد (screen تازه فوراً state را می‌گیرد)، تکراری‌ها را خودش حذف می‌کند، و Kotlin خالص است؛ پس engine بدون Android test می‌شود.
  • «چرا Volatile برای lastFetch و Atomic برای بقیه؟» lastFetch فقط نوشته و خوانده می‌شود (هیچ «بخوان، تغییر بده، بنویس» ی ندارد)، پس visibility کافی است. بقیه increment یا compare-and-set لازم دارند.

پل: «حالا که فیلدها را دیدیم: state چه مقدارهایی می‌گیرد و کی عوض می‌شود؟»

فصل ۴ — جعبه چطور حالت عوض می‌کند

اسلاید ۵ · حدود ۳ دقیقه

ایده (برای خودتان)

هفته‌ی پیش سه حالت را دیدیم. امروز انتقال‌ها را. همه در بدنه‌ی fetch اتفاق می‌افتند:

// start of every fetch:
_state.value = current?.let { Success(it, refreshing = true) } ?: Loading
// success:
_state.value = Success(data, refreshing = false)
// gave up after retries:
_state.value = if (existing != null) Success(existing, refreshing = false)
               else Failure(AppError.from(throwable))

نتیجه‌ی مهم: Loading فقط وقتی است که هیچ data ای نداریم. بعد از اولین موفقیت، screen هیچ‌وقت دوباره spinner تمام‌صفحه یا صفحه‌ی error نمی‌بیند (مگر جعبه evict شود و از صفر ساخته شود). این همان stale-while-revalidate ی React Query است.

روی اسلاید، build به build

  1. → Loading ← fetch موفق ← Success.
  2. → refetch شروع شد: Success با refreshing = true. «data روی صفحه می‌ماند.»
  3. → refetch موفق: Success با data ی جدید.
  4. → refetch ناموفق: باز Success با data ی قبلی. «error نه. اسلاید ۱۸.»
  5. → Loading ← ناموفق بعد از retryها ← Failure.
  6. → Failure ← کاربر Retry زد ← Loading.
  7. → جمله‌ی پایین.

از کلاس بپرسید

  • «کاربر در لیست است و refetch شکست می‌خورد. چه می‌بیند؟» (همان لیست. هیچ تغییری.)

اگر پرسیدند

  • «isLoading در QueryResult یعنی کدام؟» isLoading هم Loading را می‌گیرد و هم Success با refreshing. برای spinner تمام‌صفحه از QueryContent استفاده کنید که فقط روی Loading spinner می‌کشد.

پل: «این انتقال‌ها وقتی شروع می‌شوند که fetch صدا زده شود. ولی fetch همیشه request نمی‌زند.»

فصل ۵ — fetch: سه سؤال

اسلاید ۶ · حدود ۳ دقیقه

ایده (برای خودتان)

کد روی اسلاید ساده‌شده است. کد واقعی (QueryEntry.fetch) همین سه سؤال را می‌پرسد، با چند جزئیات:

  1. request در راه است؟ if (!force && inFlight.get()?.isActive == true) return.
  2. fresh است؟ servedFromCache = !force && !shouldFetch() && current != null. اگر بله، فقط یک metric «cache hit» ثبت می‌شود و برمی‌گردد.
  3. وگرنه: بدنه با scope.async(start = LAZY) ساخته می‌شود ولی هنوز شروع نمی‌شود. بعد در یک حلقه‌ی compare-and-set خودش را در inFlight نصب می‌کند. فقط برنده start می‌شود و فقط برنده epoch جدید می‌گیرد. در آخر، inFlight با compareAndSet(deferred, null) پاک می‌شود.

force: fetchهای force (invalidate، refetch()، polling) سؤال ۱ و ۲ را رد می‌کنند. یک fetch ی force اگر request ی در راه باشد، آن را cancel می‌کند و جایش می‌نشیند (چون data ی آن request ممکن است قبل از write باشد). polling یک استثنا دارد: اگر request ی در راه باشد، اصلاً fetch نمی‌زند (اسلاید ۱۳).

روی اسلاید، build به build

  1. → سؤال ۱ و خطش. «request در راه است؟ صبر کن.»
  2. → سؤال ۲ و shouldFetch. «fresh است؟ همان را بده.»
  3. → سؤال ۳. «وگرنه یک request، با epoch جدید.»
  4. → امضای تابع و جمله‌ی force.

اگر پرسیدند

  • «چرا async lazy؟» تا بدنه قبل از برنده شدن شروع نشود. اگر eager بود، بازنده‌ها هم یک request زده بودند و بعد cancel می‌شدند.
  • «fetch روی کدام thread اجرا می‌شود؟» روی scope ی QueryClient که با @IoDispatcher inject شده. screen هیچ‌وقت block نمی‌شود.

پل: «حالا سؤال بزرگ هفته‌ی پیش: پس کِی واقعاً request می‌رود؟»

بخش ۳ — کِی request می‌رود

فصل ۶ — فقط چهار چیز request می‌فرستد

اسلاید ۷ · حدود ۳ دقیقه

کجای مسیر هستیم: جواب مستقیم «این همه request». مهم‌ترین اسلاید جلسه؛ آهسته بروید.

ایده (برای خودتان)

در کل engine فقط این چهار مسیر به fetcher() می‌رسند:

triggerکدشرط
اولین observerobserve(): if (count == 1) { if (shouldFetch()) fetch() }فقط نفر اول، و فقط اگر خالی یا stale
invalidatelastFetch = 0; if (observers > 0) fetch(force = true, manual = true)اگر کسی نگاه نمی‌کند، فقط stale علامت می‌خورد
دستیrefetch = { entry.fetch(force = true, manual = true) }pull-to-refresh یا دکمه‌ی Retry ی QueryContent
intervalحلقه‌ی startIntervalفقط وقتی screen در STARTED است و request ی در راه نیست

دو نکته‌ی ظریف که مهندس‌ها ممکن است بپرسند:

  • screen دوم fetch نمی‌کند، حتی اگر data stale باشد. فقط وقتی observers از ۰ به ۱ می‌رود fetch بررسی می‌شود. پس اگر Dashboard باز است و data stale شده، باز کردن Wallet با همان key request نمی‌زند. این عمدی است: کسی که الان نگاه می‌کند همان data را دارد، و refetch برای data ی زنده کار interval است.
  • عوض شدن key یا enabled مثل یک screen جدید است. DisposableEffect(key, enabled) از جعبه‌ی قبلی unobserve و جعبه‌ی جدید را observe می‌کند.

روی اسلاید، build به build

  1. → FIRST OBSERVER · → INVALIDATE · → MANUAL · → INTERVAL.
  2. → کارت «همه‌ی چیزهای دیگر: صفر request».
«جعبه فقط وقتی به سرور می‌رود که دلیل داشته باشد: خالی است، stale است، یا می‌دانیم عوض شده. هر چیز دیگری صفر request است.»

از کلاس بپرسید

  • «recomposition چند request می‌زند؟» (صفر. remember(key) جعبه را نگه می‌دارد و fetch فقط در effectها صدا زده می‌شود.)
  • «کاربر ۲۰ بار گوشی را بچرخاند؟» (صفر، تا وقتی fresh است.)

پل: «اولین trigger گفت "خالی یا stale". stale یعنی چه؟»

فصل ۷ — staleTime

اسلاید ۸ · حدود ۳ دقیقه

ایده (برای خودتان)

private fun shouldFetch(): Boolean =
    current == null || (now() - lastFetch) > staleTime

lastFetch فقط با fetch موفق یا setData جلو می‌رود؛ invalidate آن را ۰ می‌کند. پیش‌فرض staleTime ۵ دقیقه است (QueryClient.DEFAULT_STALE_TIME_MS).

// QueryEntry

        })
    }

// QueryEntry: one loop per box
fun startInterval(interval: Long) {
    if (observers.get() <= 0 || interval <= 0) return
    if (intervalCount.incrementAndGet() == 1) {
        intervalJob.set(scope.launch {
            while (isActive && intervalCount.get() > 0 && observers.get() > 0) {
                delay(interval)
                if (inFlight.get()?.isActive != true) fetch(force = true, manual = false)
            }
        })
    }
}

فصل ۱۴ — payload

اسلاید ۱۵ · حدود ۲ دقیقه

ایده (برای خودتان)

جواب صادقانه: engine به اندازه‌ی هر جواب کاری ندارد؛ fetcher هر چه برگرداند، همان cache می‌شود. کار engine کم کردن تعداد request است، و request ی که نرود صفر byte است. اندازه‌ی هر جواب تصمیم API است، و چند ابزار با engine کنار هم کار می‌کنند:

  • خلاصه در برابر کامل: لیست با endpoint ی خلاصه (id، عنوان، قیمت)، صفحه‌ی جزئیات با endpoint ی کامل. دو key، دو جعبه.

  • gzip: OkHttp به‌طور پیش‌فرض Accept-Encoding: gzip می‌فرستد.

حافظه: فقط جعبه‌های زنده و جعبه‌های ۱۰ دقیقه‌ی اخیر. هر جعبه یک مرجع به همان object ی است که fetcher برگرداند؛ کپی نمی‌شود. اگر یک لیست بزرگ است، همان لیستی است که ViewModel هم نگه می‌داشت؛ با این فرق که یک بار، نه برای هر screen.

مشکل: فرم «ویرایش پروفایل» با نام فعلی شروع می‌شود (server data)، ولی از لحظه‌ای که کاربر تایپ می‌کند، متن مال screen است (UI state). اگر این دو را قاطی کنیم، یکی از دو باگ را داریم:

جواب کوتاه بدهید و اگر لازم شد کد را در Android Studio باز کنید. جواب‌ها با کد ComposeCleanArch چک شده‌اند.

۱. request و کارایی

با این همه screen، سرور زیر بار نمی‌رود؟ برعکس: هر key حداکثر یک request در لحظه، هیچ request ی برای data ی fresh، و polling فقط روی صفحه. نسبت به ViewModel ی که در هر init fetch می‌کند، request کمتر است.

اگر staleTime را ۰ بگذارم؟ هر بار که اولین screen جعبه را باز کند refetch می‌شود (ولی data ی قبلی فوراً نشان داده می‌شود). screen دوم با همان key هنوز request نمی‌زند، چون فقط observer ی اول fetch را بررسی می‌کند.

recomposition request می‌زند؟ نه. fetch فقط در effectها (DisposableEffect، LaunchedEffect) و با کار کاربر صدا زده می‌شود.

collectAsState در هر screen گران نیست؟ نه. StateFlow فقط وقتی emit می‌کند که مقدار عوض شود، و QueryResult با remember(state, isManualRefetch) ساخته می‌شود.

۲. data زنده

چرا WebSocket پیش‌فرض نیست؟ چون بیشتر data زنده نیست، و WebSocket برای هر endpoint کار backend می‌خواهد. engine هر دو را پشتیبانی می‌کند: polling داخلی، push از طریق setData.

polling وقتی دو screen دو interval مختلف می‌خواهند؟ یک حلقه برای جعبه، با interval ی اولین screen. اگر لازم است، key را جدا کنید.

بعد از برگشت از background، data کهنه نمی‌ماند؟ برای screen ی با polling، حلقه با STARTED دوباره شروع می‌شود و اولین tick بعد از یک دوره می‌آید. برای بقیه، تا یکی از چهار trigger اتفاق نیفتد نه. این یکی از محدودیت‌های اسلاید ۲۶ است.

۳. state

QueryResult را می‌شود به یک ViewModel پاس داد؟ نه؛ hook فقط داخل Compose کار می‌کند. اگر ViewModel به server data نیاز دارد، از repository بگیرد. ولی معمولاً لازم نیست: screen هر دو را می‌گیرد (data از hook، UI state از ViewModel) و ترکیبشان می‌کند. جلسه‌ی ۳.

derived state، مثلاً جمع سبد خرید؟ از data حساب کنید، نگه ندارید: val total = remember(cart.data) { cart.data?.sumOf { it.price } }. یک منبع حقیقت.

دو query که به هم وابسته‌اند؟ enabled روی دومی: useOrders(userId, QueryOptions(enabled = userId != null))، و id داخل key.

optimistic update؟ با queryClient.setData ممکن است و epoch مراقب است که یک fetch ی قدیمی رویش ننویسد. ولی rollback ی خودکار نداریم؛ در onError باید خودتان invalidate کنید. برای پول، اول جواب سرور را صبر کنید.

۴. engine

چرا خود TanStack Query را port نکردیم؟ نسخه‌ی Kotlin ندارد، و چیزی که لازم داشتیم حدود ۸۸۰ خط شد. هر کس تیم می‌تواند کلش را بخواند.

چرا fetcher یک lambda است و نه یک interface؟ چون هر hook فقط یک تابع suspend لازم دارد که repository را صدا بزند. interface فقط boilerplate اضافه می‌کرد.

«اولین hook برنده است» یعنی چه دقیقاً؟ getOrCreate با computeIfAbsent فقط بار اول fetcher، staleTime، cacheTime و maxAttempts را می‌گیرد. hook های بعدی با همان key تنظیمات خودشان را دارند ولی نادیده گرفته می‌شوند. برای همین: هر key فقط یک hook.

OfflineForever و invalidate؟ نکته‌ی فصل ۱۱ را ببینید: اگر وقتی هیچ screen ی جعبه را نگاه نمی‌کند invalidate شود، refetch ی بعدی اتفاق نمی‌افتد تا جعبه evict شود. باگ شناخته‌شده؛ اگر کسی پیدایش کرد، درست دیده است.

metrics را کجا ببینم؟ QueryClient برای هر key QueryMetrics نگه می‌دارد: fetchCount، cacheHits، errors، averageTimeMs.

var attempt = 1
while (true) {
    try {
        val data = fetcher()
        if (epoch.get() != latestEpoch.get()) break
        lastFetch = now()
        source?.writer(data)
        _state.value = QueryState.Success(data, refreshing = false)
        break
    } catch (cancellation: CancellationException) {
        throw cancellation
    } catch (throwable: Throwable) {
        if (attempt < maxAttempts && isRetryable(throwable)) {
            delay(retryDelayMs * attempt); attempt++; continue
        }
        if (epoch.get() != latestEpoch.get()) break
        val existing = current
        _state.value = if (existing != null) QueryState.Success(existing, refreshing = false)
                       else QueryState.Failure(AppError.from(throwable))
        break
    }
}

fun setData(data: T) {
    lastFetch = now()
    latestEpoch.incrementAndGet()
    _state.value = QueryState.Success(data, refreshing = false)
    source?.let { src -> scope.launch { src.writer(data) } }
}
