نقشه‌ی جلسه‌ی ۱ — قبل از هر چیز این را بخوانید

جلسه‌ی ۱ از ۳ · The idea · حدود ۵۸ دقیقه · ۳۰ اسلاید · باز کردن اسلایدها

کار این جلسه: طرز فکر کلاس را درباره‌ی server data عوض کنید. امروز engine را باز نمی‌کنیم؛ فقط می‌گوییم چرا و چه چیزی. هر سؤالی درباره‌ی «کِی fetch می‌کند / کِی پاک می‌شود / retry» → «سؤال خوبی است؛ دقیقاً موضوع جلسه‌ی بعد.»

جمله‌ی اصلی (اسلاید ۸ می‌گویید، اسلاید ۲۸ تکرار می‌کنید):

«server data مال ما نیست؛ یک کپی است. پس به جای اینکه هر screen کپی خودش را در یک ViewModel نگه دارد، یک cache مشترک داریم و screen فقط می‌گوید چه data‌ای می‌خواهد.»

فصل ۲ — قبل از شروع: React Query به زبان ساده

اسلایدهای ۳ تا ۶ · حدود ۹ دقیقه

کجای مسیر هستیم: یک heads-up برای کسانی که هیچ‌وقت این نوع معماری را ندیده‌اند. با زبان ساده و یک داستان؛ هنوز نه مشکل اپ خودمان را گفته‌ایم، نه کد Kotlin.

ایده (برای خودتان)

کل ایده با یک داستان ساده گفته می‌شود: تابلوی دفتر.

  • بدون تابلو: سه همکار هر کدام خودشان به بانک زنگ می‌زنند تا موجودی را بپرسند. سه تماس برای یک عدد، و بعد از یک خرید، هر کس عدد قدیمی خودش را دارد.
  • با تابلو: یک نفر یک بار زنگ می‌زند و عدد را روی تابلو می‌نویسد؛ بقیه فقط تابلو را می‌خوانند. بعد از خرید، تابلو پاک می‌شود و فقط یک بار دوباره زنگ زده می‌شود.
در داستاناسم فنی
تابلوcache
خواندن تابلوquery
خریدmutation
پاک کردن تابلوinvalidate
اسم روی تابلو («موجودی USDT»)key

در دنیای وب اسم این ایده React Query است (امروز TanStack Query، از ۲۰۱۹). در کد فقط دو چیز می‌گویید: queryKey (چه data‌ای) و queryFn (از کجا). بقیه را خودش انجام می‌دهد.

روی اسلاید ۳ — داستان تابلو

  1. → بدون تابلو: «فرض کنید در یک دفتر سه همکار هر کدام موجودی حساب شرکت را لازم دارند. هر کدام خودش به بانک زنگ می‌زند. سه تماس برای یک عدد. وقتی یکی خرید کرد، دو نفر دیگر هنوز عدد قدیمی را دارند.»
  2. → با تابلو: «حالا یک تابلو در دفتر هست. یک نفر یک بار زنگ می‌زند و می‌نویسد. بقیه فقط به تابلو نگاه می‌کنند.»
  3. → «بعد از خرید، تابلو پاک می‌شود و فقط یک بار دوباره زنگ زده می‌شود.»
  4. → «کل امروز همین داستان است، با اسم‌های فنی: تابلو یعنی cache، خواندن تابلو یعنی query، خرید یعنی mutation، پاک کردن تابلو یعنی invalidate.»

روی اسلاید ۴ — اسم این ایده: React Query

  1. → Screen. → «به جای اینکه خودش request بزند، می‌گوید چه data‌ای می‌خواهد.» → «این درخواست به cache می‌رود؛ همان تابلو.» → «cache فقط وقتی لازم است به سرور می‌رود.»
  2. → سه کلمه را تکرار کنید: query خواندن، mutation عوض کردن، cache کپی مشترک.
  3. → «یک library معروف در وب، از ۲۰۱۹. امروز همین ایده را در Compose می‌بینیم.»

روی اسلاید ۵ — در کد فقط دو چیز

«کد JavaScript است، ولی لازم نیست JavaScript بلد باشید.»

  1. → queryKey: «چه data‌ای؟ اسمش، مثل اسم روی تابلو.»
  2. → queryFn: «از کجا بگیرم؟ مثل تماس با بانک.»
  3. → خط اول: «چه پس می‌گیرید: data خود data، isLoading یعنی هنوز در راه است، error یعنی اگر نشد.»
  4. → «همین. بقیه را خودش انجام می‌دهد.»

روی اسلاید ۶ — بقیه را خودش انجام می‌دهد

هر کارت را با داستان تابلو بگویید:

  1. → یادش می‌ماند (cache): عدد روی تابلو می‌ماند؛ دفعه‌ی بعد فوراً می‌بینید.
  2. → فقط یک بار می‌پرسد (de-duplication): سه نفر با هم بپرسند، یک تماس.
  3. → وقتی کهنه شد، دوباره می‌پرسد (refetch): عدد قدیمی روی تابلو می‌ماند تا جدید برسد.
  4. → اگر نشد، دوباره امتحان می‌کند (retry): بانک جواب نداد؟ چند ثانیه بعد دوباره.
  5. → بعد از تغییر، خبردار می‌شود (invalidate): بعد از خرید، تابلو پاک و دوباره پر می‌شود.
  6. → «شما فقط می‌گویید چه data‌ای.»

از کلاس بپرسید

  • «در اپ خودمان، کدام data مثل همان عدد روی تابلو است؛ چیزی که چند screen می‌خواهند؟» (موجودی، پروفایل، سفارش‌ها)

نکته: اگر کلاس از قبل React Query را می‌شناسد، این بخش را به ۳ دقیقه کوتاه کنید و فقط اسلاید ۳ و ۶ را بگویید.

پل: «خب، این ایده بود. حالا ببینیم همین مشکل در اپ خودمان چه شکلی است.»

فصل ۳ — Cold open: چند کپی؟

اسلاید ۷ · حدود ۳ دقیقه

کجای مسیر هستیم: مشکل را نشان می‌دهیم، با چشم، قبل از هر توضیحی.

ایده (برای خودتان)

امروز هر screen که موجودی را نشان می‌دهد، ViewModel خودش را دارد و ViewModel یک MutableStateFlow جدا. پس اگر سه screen موجودی را نشان دهند، سه کپی از یک عدد در حافظه داریم، سه request برای گرفتنش، و بعد از هر تغییر، هیچ‌کدام خودشان خبردار نمی‌شوند. هر تیم این را با event bus یا callback یا «برگشتن به صفحه» وصله می‌کند.

روی اسلاید، build به build

  1. سؤال روی صفحه است. بلند بپرسید و صبر کنید جواب بدهند: «الان اپ ما چند کپی از موجودی کیف پول دارد؟»
  2. → سه phone: «موجودی در Dashboard هست، در Wallet، در Buy.»
  3. → سه ViewModel: «هر screen، ViewModel خودش را دارد. یعنی سه کپی.»
  4. → سه خط به سرور: «سه request برای یک عدد.»
  5. → خرید: سرور ۱٬۲۳۰ می‌شود و سه phone قرمز ۱٬۲۵۰ می‌مانند. «کاربر خرید کرد. سرور عدد جدید دارد. ولی هر سه screen هنوز عدد قدیمی را نشان می‌دهند، تا یکی دستی به هر ViewModel بگوید reload کن.»

از کلاس بپرسید

  • «امروز در کد خودمان، بعد از یک خرید چطور به screenهای دیگر می‌گوییم refresh کنند؟» (جواب‌های معمول: event bus، callback، shared ViewModel، یا اصلاً نمی‌گوییم و کاربر pull-to-refresh می‌کند.)

پل: «این مشکل کد نیست؛ مشکل طرز فکر است.»

فصل ۴ — جمله‌ی اصلی، و سه چیزی که امروز می‌سازیم

اسلایدهای ۸ و ۹ · حدود ۴ دقیقه

کجای مسیر هستیم: مهم‌ترین لحظه‌ی جلسه. آرام و با مکث.

ایده (برای خودتان)

data‌ای که از سرور می‌آید مال ما نیست؛ صاحبش سرور است. ما فقط یک کپی داریم که از لحظه‌ی رسیدن شروع به کهنه شدن می‌کند. کپی‌ها نیازهای مشخصی دارند: یک جا نگه داشته شوند، بین همه مشترک باشند، و بعد از تغییر تازه شوند. این‌ها دقیقاً کار یک cache است. ViewModel ابزار نگه‌داری state است، نه cache؛ برای همین هر ViewModel یک cache ناقص و تکراری می‌سازد.

فصل ۵ — وب همین مشکل را داشت

اسلاید ۱۰ · حدود ۳ دقیقه

کجای مسیر هستیم: یک سفر کوتاه به وب، تا ببینند این مشکل جهانی است و یک راه‌حل امتحان‌شده دارد.

ایده (برای خودتان)

تا حدود ۲۰۱۹ بیشتر اپ‌های React، server data را در Redux نگه می‌داشتند: یک store مرکزی. برای گرفتن یک لیست:

  • سه action (یعنی event): LOADING، SUCCESS، FAILURE
  • یک reducer: تابعی که با هر action، state جدید می‌سازد (isLoading، data، error)
  • یک useEffect که بعد از اولین render، load را صدا می‌زند

ترجمه به اندروید: action + reducer = UiState و بدنه‌ی load() در ViewModel؛ useEffect = LaunchedEffect. لازم نیست Redux بلد باشید؛ فقط باید شباهت را ببینید.

روی اسلاید، build به build

  1. → ستون articles: «برای گرفتن یک لیست در React: سه action، یک reducer، یک useEffect.»
  2. → ستون‌های profile و orders: «و برای هر request دیگر، همه‌ی این‌ها دوباره.»
  3. → «آشنا نیست؟» (صبر کنید) «این همان UiState + ViewModel + LaunchedEffect ماست.»

اگر پرسیدند

  • «Redux چیست؟» «یک store مرکزی برای state. action یعنی event، reducer یعنی تابعی که state جدید می‌سازد.»

پل: «و یک نفر در دنیای React این را حل کرد.»

فصل ۶ — React Query

اسلاید ۱۱ · حدود ۳ دقیقه

کجای مسیر هستیم: راه‌حل وب. هنوز اندروید نیست.

ایده (برای خودتان)

Tanner Linsley در ۲۰۱۹ React Query را ساخت؛ امروز اسمش TanStack Query است. ایده‌اش یک جمله است: server data، state نیست؛ cache است. پس به جای اینکه هر component مدیریتش کند، یک cache مرکزی این کارها را یک بار و درست انجام می‌دهد و component فقط دو چیز می‌گوید:

  1. queryKey: چه data‌ای (مثلاً ['articles', source])
  2. queryFn: از کجا (تابعی که API را صدا می‌زند)

isLoading و error را خود کتابخانه برمی‌گرداند.

روی اسلاید، build به build

  1. جمله‌ی بزرگ: «کل ایده همین است.»
  2. → کد: «component فقط می‌گوید چه data‌ای (queryKey) و از کجا (queryFn). loading و error را کتابخانه می‌دهد.»
  3. → چهار کار: «cache مشترک، فقط یک request همزمان، refetch بعد از تغییر، retry و polling. این‌ها دیگر کار هر component نیست.»

اگر پرسیدند

  • «پس این library را در اندروید استفاده می‌کنیم؟» «نه. TanStack Query برای JavaScript است. ما فقط ایده و شکل API را گرفتیم و در Kotlin ساختیم.»

پل: «چرا فکر می‌کنیم این در اندروید جواب می‌دهد؟»

فصل ۹ — یک جعبه‌ی مشترک

اسلاید ۱۴ · حدود ۳ دقیقه

کجای مسیر هستیم: راه‌حل، به همان شکل اسلاید ۷: همان سه phone، ولی این بار با یک جعبه.

ایده (برای خودتان)

به جای اینکه هر ViewModel جعبه‌ی خودش را داشته باشد، یک جعبه در یک جای مشترک نگه می‌داریم و همه‌ی screenها همان را می‌خوانند. اسم این جعبه در کد QueryEntry است. نتیجه:

  • یک جعبه → عدد هیچ‌وقت بین screenها فرق نمی‌کند.
  • یک request جعبه را پر می‌کند → همه نتیجه را می‌بینند.
  • بعد از خرید، همین یک جعبه refresh می‌شود → همه با هم عوض می‌شوند.

روی اسلاید، build به build

  1. سه phone (مثل اسلاید ۷).
  2. → جعبه و سه خط: «یک جعبه به اسم QueryEntry، با key "wallet.balance.USDT". هر سه screen همین را می‌خوانند. یک request.»
  3. → خرید: جعبه می‌درخشد، هر سه phone با هم سبز می‌شوند. «خرید → invalidate → یک refetch → همه با هم. هیچ‌کس دستی کاری نکرد.» به ردیف requests اشاره کنید: ۱ بود، ۲ شد؛ نه ۶.

اگر پرسیدند: «فرقش با shared ViewModel چیست؟»

این سؤال تقریباً حتماً پرسیده می‌شود.

در یک جمله: shared ViewModel یک state holder را مشترک می‌کند؛ جعبه یک cache از server data است که با key مشترک می‌شود.

۱. هویت: با چه چیزی پیدا می‌شوند؟

  • shared ViewModel با owner و key پیدا می‌شود. هر screen که همان owner (مثلاً Activity یا یک nav graph) و همان key را بگیرد، همان instance را می‌گیرد، و عمرش به همان owner بسته است.
  • جعبه با key داده و QueryClient پیدا می‌شود (مثل "profile.42"). مهم نیست screen کجای navigation است یا چقدر عمر می‌کند.

۲. مهم‌ترین فرق: عمر و cache

یک سناریو:

  1. screen A پروفایل کاربر ۴۲ را می‌خواهد.
  2. کاربر به screen B می‌رود که آن هم کاربر ۴۲ را می‌خواهد.
  3. بعداً به A برمی‌گردد.
  • با shared ViewModel: data تا وقتی owner زنده است می‌ماند. اگر ViewModel به یک destination بسته باشد و آن destination از back stack بیرون برود، data پاک می‌شود. اگر به Activity بسته باشد، تا آخر عمر اپ می‌ماند، ولی هیچ‌وقت خودش کهنه یا تازه یا پاک نمی‌شود مگر خودتان بنویسید؛ و کم‌کم همه‌ی data مشترک اپ در همان یک ViewModel جمع می‌شود.
  • با جعبه: وقتی A رفت، data در cache می‌ماند؛ B با همان key همان را فوراً می‌گیرد. حتی وقتی هیچ screenی نگاهش نمی‌کند، تا cacheTime نگه داشته می‌شود و بعد خودش پاک می‌شود. و اگر کهنه شده باشد (staleTime)، خودش دوباره می‌گیرد.

۳. جعبه فقط «اشتراک» نیست

کِی shared ViewModel درست است: برای UI state مشترک؛ مثلاً فرمی که بین مراحل ثبت‌نام مشترک است. نه برای server data.

آماده برای گفتن:

«shared ViewModel یک state holder است که بین screenهایی با همان owner مشترک می‌شود، و عمرش به همان owner بسته است. جعبه یک cache از server data است که با key پیدا می‌شود: هر screenی در اپ با همان key همان data را می‌گیرد، data بعد از رفتن screen هم تا cacheTime می‌ماند، و قانون‌های staleTime، refetch، retry و invalidate از قبل در آن هست. با shared ViewModel همه‌ی این‌ها را باید خودتان بنویسید. shared ViewModel برای UI state مشترک عالی است، مثل فرم چندمرحله‌ای؛ برای server data، cache.»

فصل ۱۱ — key: اسم جعبه

اسلایدهای ۱۶ و ۱۷ · حدود ۶ دقیقه

کجای مسیر هستیم: قطعه‌ی دوم از سه کلمه‌ی امروز. key ساده به نظر می‌رسد، ولی باگ‌هایش بی‌صدا هستند؛ پس وقت بگذارید.

ایده (برای خودتان)

key هویت جعبه است:

  • key یکسان = همان جعبه = data مشترک.
  • key متفاوت = جعبه‌ی جدا = data جدا.

engine هیچ چیز دیگری را نگاه نمی‌کند: نه اینکه کدام screen است، نه اینکه fetcher چیست. فقط اسم. وقتی screenی جعبه‌ای را با یک key می‌خواهد، QueryClient در map دنبال همان اسم می‌گردد؛ اگر پیدا کرد همان را می‌دهد، اگر نه یکی جدید می‌سازد.

تشبیه: برچسب روی تابلو

همان تابلوی دفتر از اول جلسه، حالا چند بخش دارد و هر بخش یک برچسب: «موجودی USDT»، «موجودی BTC»، «سفارش‌های باز». key همان برچسب است. هر کس دنبال «موجودی USDT» بگردد، به همان بخش می‌رسد. اگر دو چیز متفاوت را با یک برچسب بنویسیم، روی هم نوشته می‌شوند.

قانون ۱: هر چیزی که نتیجه را عوض می‌کند، باید در key باشد

قاعده‌ی سرانگشتی: به پارامترهای fetcher نگاه کنید. هر پارامتری که در fetcher هست، باید در key هم باشد (source، page، فیلتر، id، ارز).

قانون ۲: key سلسله‌مراتبی است، مثل پوشه‌ها

فایده: می‌توانیم یک گروه کامل را با هم refetch کنیم:

  • invalidate("articles.headlines.techcrunch.1"): فقط همین یک جعبه.
  • invalidateMatching("articles\\..*"): هر key که با articles. شروع می‌شود؛ همه‌ی صفحه‌ها و bookmarks.

اگر پرسیدند \\..* چیست: یک regex است. \\. یعنی یک نقطه‌ی واقعی و .* یعنی هر چیزی بعدش. (دو backslash چون داخل رشته‌ی Kotlin است.)

مثال واقعی: کاربر زبان خبرها را عوض می‌کند. همه‌ی لیست‌های خبر باید دوباره گرفته شوند؛ با یک invalidateMatching همه با هم.

قانون ۳: key را دستی تایپ نکنید

داستان باگ:

  1. hook موجودی را با "wallet.balance.usdt" (حروف کوچک) می‌خواند.
  2. خرید بعد از موفقیت "wallet.balance.USDT" (حروف بزرگ) را invalidate می‌کند.
  3. این دو، دو رشته‌ی متفاوت‌اند، پس دو جعبه.
  4. خرید موفق است، ولی جعبه‌ای که screen نشان می‌دهد هیچ‌وقت invalidate نمی‌شود. موجودی هرگز تازه نمی‌شود، و هیچ error‌ی هم نمی‌بینید.

یک تعریف، یک جا. اگر کسی اسم تابع را اشتباه بنویسد، compiler خطا می‌دهد؛ رشته‌ی دستی را هیچ‌کس چک نمی‌کند.

  • «بعد از لغو یک سفارش، کدام جعبه‌ها باید invalidate شوند؟» (جواب: همه‌ی لیست‌های سفارش با invalidateMatching("orders\\.list\\..*")، و جزئیات همان سفارش.)

اگر پرسیدند

  • «شناسه‌ی کاربر هم باید در key باشد؟» معمولاً نه؛ موقع logout، queryClient.clear() همه‌ی جعبه‌ها را پاک می‌کند. اگر اپ چند حساب همزمان دارد، بله.
  • «چرا همه‌ی لیست‌ها را invalidate کنیم؟ فقط همان لیستی که سفارش در آن بود کافی نیست؟» نه. چهار دلیل، به ترتیب:
    1. یک سفارش در چند جعبه است. ممکن است هم در orders.list.open.1 باشد و هم در orders.list.all.3. بعد از لغو باید از لیست «باز» بیرون برود و به لیست «بسته» اضافه شود؛ پس لیستی که الان اصلاً این سفارش را ندارد هم غلط شده است.
    2. صفحه‌بندی همه‌چیز را جابه‌جا می‌کند. وقتی یک آیتم از صفحه‌ی ۱ حذف شود، اولین آیتم صفحه‌ی ۲ به صفحه‌ی ۱ می‌آید و همین‌طور تا آخر. همه‌ی صفحه‌های بعدی هم غلط می‌شوند.
    3. QueryClient محتوای جعبه‌ها را نمی‌شناسد. فقط key ها را می‌بیند. برای اینکه بفهمیم سفارش در کدام جعبه است باید داخل data ی همه‌ی جعبه‌ها را بگردیم؛ پیچیده است و به‌خاطر دلیل ۲ باز هم جواب درست نمی‌دهد.
    4. invalidate ارزان است (مهم‌ترین نکته). کد QueryEntry.invalidate(): 
      fun invalidate() {
    lastFetch = 0L
    if (observers.get() > 0) fetch(force = true, manual = true)
}
      فقط جعبه‌ای که الان روی صفحه است (observer دارد) همین الان fetch می‌شود؛ معمولاً یکی یا دوتا. بقیه هیچ request‌ی نمی‌فرستند؛ فقط stale علامت می‌خورند و وقتی کاربر دوباره آن صفحه را باز کند fetch می‌شوند. پس «همه‌ی لیست‌ها» یعنی ده request نیست.
    جمله‌ی کلاس: «invalidate دقیق سخت است و راحت اشتباه می‌شود؛ invalidate کمی گسترده ساده است، همیشه درست است و تقریباً هزینه‌ای ندارد. دومی را انتخاب می‌کنیم.»
  • «پس چرا کل cache را invalidate نکنیم؟» چون لغو سفارش روی محصولات و پروفایل اثری ندارد. قانون: هر چیزی که ممکن است این سفارش را نشان دهد، نه بیشتر. برای همین orders\\.list\\..*، نه .*.
  • «چرا لیست را خودمان با setData درست نکنیم؟» می‌شود (optimistic update)، ولی باید منطق سرور یعنی ترتیب، فیلتر و صفحه‌بندی را در client دوباره بنویسیم. برای یک آیتم مثل orders.detail.42 ارزش دارد؛ برای لیست صفحه‌بندی‌شده معمولاً نه.
  • «چرا key رشته است و نه یک data class؟» چون رشته‌ی سلسله‌مراتبی اجازه می‌دهد یک گروه را با یک الگو invalidate کنیم. برای اینکه typo نشود، رشته‌ها فقط در object کنار Api ساخته می‌شوند.

پل: «همه‌ی این جعبه‌ها کجا نگه داشته می‌شوند؟»

فصل ۱۲ — QueryClient: یک map

اسلاید ۱۸ · حدود ۲ دقیقه

کجای مسیر هستیم: قطعه‌ی سوم.

ایده (برای خودتان)

QueryClient یک ConcurrentHashMap<String, QueryEntry> است، و یک @Singleton در Hilt. وقتی screenی جعبه‌ای را با key می‌خواهد، computeIfAbsent(key) صدا زده می‌شود: اگر جعبه هست همان را برمی‌گرداند، اگر نیست می‌سازد و در map می‌گذارد. چون کل اپ یک map دارد، data بین screenها مشترک است. (کد روی اسلاید ساده‌شده است؛ در کد واقعی getOrCreate چند پارامتر دیگر هم می‌گیرد، مثل fetcher و staleTime.)

چرا ConcurrentHashMap و نه HashMap؟ (قدم به قدم)

قدم ۱: چه کسی، از کدام thread، به map دست می‌زند؟

چه کسیکجاthread
hook ها (useQuery)getOrCreate → computeIfAbsentmain (composition)
prefetchgetOrCreate داخل scope.launchIO
پاک کردن جعبه بعد از cacheTimeevict → computeIfPresentIO
mutation یا هر کلاسی که QueryClient را inject کردهinvalidate / invalidateMatchingهر thread‌ی

پس map همزمان از main و IO خوانده و نوشته می‌شود. اینجا HashMap امن نیست.

قدم ۲: با HashMap چه چیزی خراب می‌شود؟

  1. دو جعبه برای یک key. screen روی main و prefetch روی IO همزمان می‌پرسند «key هست؟». هر دو جواب «نه» می‌گیرند و هر کدام یک جعبه‌ی جدید می‌سازند. دو request می‌رود؛ یکی از جعبه‌ها جای دیگری را در map می‌گیرد و screen‌ی که جعبه‌ی دیگر را دارد دیگر هیچ invalidate‌ی را نمی‌بیند. کل قانون «یک key، یک جعبه» شکسته است.
  2. خرابی خود map. HashMap موقع بزرگ شدن (resize) جدولش را بازسازی می‌کند. اگر thread دیگری همان لحظه بنویسد، ممکن است entry گم شود.
  3. crash موقع invalidateMatching. این تابع روی همه‌ی keyها می‌چرخد. اگر وسط چرخش، screen‌ی key جدیدی اضافه کند، HashMap با ConcurrentModificationException crash می‌کند.

قدم ۳: ConcurrentHashMap هر سه را حل می‌کند.

  • computeIfAbsent atomic است: «نگاه کن، اگر نبود بساز، بگذار» یک قدم است. thread دوم صبر می‌کند و همان جعبه‌ی اول را می‌گیرد.
  • iterator آن weakly consistent است: موقع چرخیدن روی keyها، اضافه شدن key جدید crash نمی‌دهد.
  • evict هم از computeIfPresent استفاده می‌کند. داخل همان قدم atomic دوباره چک می‌کند که آیا screen‌ی همین الان دوباره به جعبه برگشته است؛ اگر برگشته، جعبه را پاک نمی‌کند.
private fun evict(key: String) {
    entries.computeIfPresent(key) { _, entry ->
        if (entry.hasNoObservers()) { entry.cleanup(); null } // null = remove
        else entry                                            // re-observed: keep
    }
}

قدم ۴: چرا synchronized یا Mutex نه؟

  • synchronized روی کل map: هر خواندن، حتی روی main thread، باید منتظر بقیه بماند. ConcurrentHashMap خواندن را بدون قفل انجام می‌دهد و فقط همان قسمت از جدول را که در آن می‌نویسد قفل می‌کند.
  • Mutex ی coroutine: lock() یک تابع suspend است، ولی getOrCreate مستقیم از composition صدا زده می‌شود که suspend نیست.

جمله‌ی کلاس: «map از چند thread استفاده می‌شود. ConcurrentHashMap تضمین می‌کند هر key فقط یک جعبه داشته باشد، بدون اینکه main thread منتظر بماند.»

روی اسلاید، build به build

  1. → کد: «یک map از key به جعبه.»
  2. → «key هست؟ همان جعبه. پس screen دوم جعبه‌ی screen اول را می‌گیرد.»
  3. → «key نیست؟ یک جعبه‌ی جدید.»
  4. → «یک Singleton در Hilt؛ کل اپ یک map.»

اگر پرسیدند

  • «مگر Compose همه‌چیز را روی main اجرا نمی‌کند؟ پس چرا thread-safe؟» hook ها بله، ولی prefetch و evict روی IO اجرا می‌شوند، و invalidate از هر جایی که QueryClient را inject کرده صدا زده می‌شود.
  • «خود QueryEntry هم thread-safe است؟» بله؛ state آن یک StateFlow است و شمارنده‌ها Atomic. جزئیاتش جلسه‌ی بعد.
  • «چیزی هست که باید مراقبش بود؟» lambda ی computeIfAbsent باید کوتاه باشد و دوباره به همان map دست نزند. برای همین فقط QueryEntry را می‌سازد؛ fetch بعداً و بیرون از آن شروع می‌شود.

فصل ۱۷ — useMutation و invalidate

اسلاید ۲۴ · حدود ۴ دقیقه

کجای مسیر هستیم: آخرین ابزار؛ و جواب cold open (اسلاید ۷): «بعد از خرید، چطور همه‌ی screenها خبردار می‌شوند؟» تا اینجا فقط خواندن دیدیم. حالا نوشتن.

ایده با داستان تابلو

یادتان هست؟ روی تابلو نوشته «موجودی USDT: ۱۰۰». همه به تابلو نگاه می‌کنند (این query است).

حالا یک نفر ۲۰ USDT خرج می‌کند (این mutation است). در بانک موجودی شد ۸۰، ولی روی تابلو هنوز ۱۰۰ نوشته. تابلو غلط است.

راه حل: کسی که خرید کرد، یک کار کوچک می‌کند: روی عدد تابلو یک علامت «قدیمی است» می‌زند (این invalidate است). هر کس الان به تابلو نگاه می‌کند، می‌بیند علامت خورده، دوباره به بانک زنگ می‌زند و عدد درست را می‌نویسد.

نکته‌ی مهم: کسی که خرید کرد لازم نیست بداند چه کسانی به تابلو نگاه می‌کنند. فقط می‌گوید «این عدد قدیمی شد».

query و mutation کنار هم

useQuery (خواندن)useMutation (نوشتن)

جمله‌ی کوتاه برای کلاس: «query می‌پرسد، mutation عوض می‌کند، invalidate خبر می‌دهد.»

بدون useMutation چه می‌کردیم؟

با ViewModel معمولاً این‌طور بود:

  1. BuyViewModel خرید را انجام می‌داد.
  2. بعد باید به WalletViewModel می‌گفت «refresh کن». پس یا یک event bus می‌ساختیم، یا یک SharedFlow مشترک، یا موقع برگشتن از screen یک result پاس می‌دادیم.
  3. فردا یک screen سوم (مثلاً order history) هم موجودی نشان می‌داد. باید یادمان می‌ماند آن را هم به این زنجیره وصل کنیم.

یعنی screen خرید باید همه‌ی screenهای دیگر را بشناسد. هر screen جدید، یک جا برای فراموش کردن.

با useMutation: screen خرید فقط اسم data را می‌گوید: WalletKeys.balance("USDT"). هر کس آن جعبه را نگاه کند، خودش تازه می‌شود؛ امروز یک screen، فردا ده screen.

کد، خط به خط

val buy = useMutation<BuyRequest, Order>(
    mutationFn = { req -> repo.buy(req) },
    options = MutationOptions(
        invalidateKeys = listOf(WalletKeys.balance("USDT")),
    ),
)
Button(onClick = { buy(request) }, enabled = !buy.isLoading) { Text("Buy") }
  1. useMutation<BuyRequest, Order>: دو type. اولی ورودی است (چه چیزی می‌فرستیم: سفارش خرید)، دومی خروجی (سرور چه برمی‌گرداند: Order ثبت‌شده).
  2. mutationFn: همان تابعی که سرور را صدا می‌زند. درست مثل fetcher در useQuery: فقط Api را صدا می‌زند؛ موفق شد نتیجه برمی‌گرداند، نشد exception می‌دهد.
  3. invalidateKeys: لیست جعبه‌هایی که بعد از موفقیت باید «قدیمی» علامت بخورند.
  4. buy(request): نتیجه‌ی useMutation را می‌شود مثل تابع صدا زد (پشتش یک operator fun invoke است). تا صدایش نزنید، هیچ اتفاقی نمی‌افتد.
  5. buy.isLoading: وقتی request در راه است true است؛ پس دکمه را غیرفعال می‌کنیم. غیر از آن buy.data، buy.error، isSuccess و isError هم دارد.

MutationOptions دو callback هم دارد: onSuccess (مثلاً برگشتن به صفحه‌ی قبل یا نشان دادن Toast) و onError.

یک خرید، قدم به قدم

فرض کنید screen کیف پول باز است و موجودی را نشان می‌دهد: ۱۰۰ USDT. کاربر در یک bottom sheet روی Buy می‌زند (۲۰ USDT).

  1. کلیک: buy(request) صدا زده می‌شود. isLoading = true؛ دکمه غیرفعال می‌شود.
  2. سرور: repo.buy(request) اجرا می‌شود. سفارش ثبت می‌شود؛ در سرور موجودی حالا ۸۰ است.
  3. invalidate: useMutation برای هر key در لیست، queryClient.invalidate(key) را صدا می‌زند. جعبه‌ی wallet.balance.USDT «قدیمی» علامت می‌خورد (در کد: lastFetch = 0).
  4. کسی نگاه می‌کند؟ بله، screen کیف پول یک observer است. پس جعبه همان لحظه fetch می‌کند. در این مدت screen هنوز ۱۰۰ را نشان می‌دهد (Success با refreshing = true)؛ spinner نمی‌آید، صفحه چشمک نمی‌زند.
  5. جواب: سرور می‌گوید ۸۰. جعبه عوض می‌شود؛ هر screen که به آن نگاه می‌کند، ۸۰ را می‌بیند.

در کل این مسیر، screen خرید و screen کیف پول هیچ کدی از هم ندارند.

اگر هیچ screenی به جعبه نگاه نکند؟

سه حالت. این را خوب بفهمید، چون معمولاً می‌پرسند:

وضعیت جعبهبعد از invalidate چه می‌شود؟
screenی الان نگاهش می‌کندهمان لحظه refetch
در cache هست، ولی screenی نگاهش نمی‌کند (مثلاً order history که بسته است)فقط علامت «قدیمی» می‌خورد؛ هیچ request نمی‌رود. دفعه‌ی بعد که screenی بازش کند، اول data قبلی را نشان می‌دهد و همان لحظه fetch می‌کند
اصلاً در cache نیستهیچ کاری لازم نیست؛ اولین بار که screenی بازش کند، به هر حال fetch می‌کند

مثال خرید BTC مهم است: یک نوشتن می‌تواند چند جعبه را عوض کند. اگر یکی را فراموش کنید، آن عدد تا وقتی staleTime تمام شود (یا polling بعدی) قدیمی می‌ماند. در فایل نمونه‌ی repo (examples/WalletHooks.kt) برای همین در onSuccess همه‌ی موجودی‌ها را یک‌جا invalidate می‌کنیم: queryClient.invalidateMatching(WalletKeys.ALL_BALANCES).

اگر خرید شکست بخورد؟

  • هیچ جعبه‌ای invalidate نمی‌شود (چیزی در سرور عوض نشده).
  • buy.error پر می‌شود (یک AppError) و onError صدا زده می‌شود؛ screen خرید پیام را نشان می‌دهد.
  • retry پیش‌فرض صفر است. چرا؟ تصور کنید request رسیده و سفارش ثبت شده، ولی جواب در راه گم شده. retry خودکار یعنی دو سفارش. اگر retryCount بدهید، فقط برای error موقت (شبکه، 5xx) تکرار می‌شود؛ هرگز برای 4xx. جزئیات در جلسه‌ی ۲.

اگر کاربر دو بار سریع بزند؟

useMutation single-flight است: تا اولی تمام نشده، صدا زدن دوم نادیده گرفته می‌شود. پس دو سفارش نمی‌رود، حتی اگر دکمه را غیرفعال نکرده باشید. (enabled = !buy.isLoading را باز هم بگذارید؛ برای کاربر واضح‌تر است.)

سه اشتباه رایج

  1. فراموش کردن یک key: خرید موفق، ولی یک screen عدد قدیمی نشان می‌دهد. با سؤال «چه چیزی در سرور عوض شد؟» پیدایش کنید.
  2. typo در key: همان باگ قانون ۳ در فصل ۱۱. key را همیشه از WalletKeys بسازید، نه با string دستی.
  3. invalidate کردن همه چیز: invalidateMatching(".*") کار می‌کند، ولی همه‌ی screenهای باز همزمان request می‌زنند. فقط چیزی را که عوض شد invalidate کنید.

فصل ۲۰ — trade-offها

اسلاید ۲۷ · حدود ۳ دقیقه

کجای مسیر هستیم: قبل از جمع‌بندی. مهندس‌ها به کسی اعتماد می‌کنند که محدودیت‌های طراحی خودش را بشناسد. اگر این‌ها را خودتان بگویید، در Q&A کسی نمی‌تواند غافلگیرتان کند.

ایده (برای خودتان)

چهار هزینه، و برای هر کدام یک قانون. هر چهار تا در کد واقعی ComposeCleanArch درست است.

۱. اولین hook تنظیمات جعبه را تعیین می‌کند.

  • در QueryClient.getOrCreate، جعبه با entries.computeIfAbsent(key) { QueryEntry(key, fetcher, staleTime, cacheTime, …) } ساخته می‌شود. lambda فقط وقتی اجرا می‌شود که key نباشد.
  • پس fetcher، staleTime و cacheTime از اولین hookی می‌آیند که جعبه را ساخت. hook دوم با همان key، تنظیمات خودش را می‌دهد ولی نادیده گرفته می‌شود؛ بدون هیچ خطا.
  • مثال: Dashboard موجودی را با staleTime سی ثانیه می‌خواهد، Wallet با پنج دقیقه. هر کدام اول باز شود، قانون همان است.
  • قانون: برای هر key فقط یک hook (مثلاً useBalance(symbol)) و همه‌ی screenها همان hook را صدا می‌زنند.

۲. یک key با دو type یعنی crash.

  • map از نوع ConcurrentHashMap<String, QueryEntry<*>> است؛ type را نگه نمی‌دارد. getOrCreate با as QueryEntry<T> و @Suppress("UNCHECKED_CAST") برمی‌گرداند.
  • اگر یک hook با key ی "wallet.balance.USDT" یک Balance بخواند و hook دیگری با همان key یک String، compiler چیزی نمی‌گوید. وقتی screen دوم data را مصرف کند، ClassCastException در runtime.
  • قانون: key فقط از XxxKeys ساخته می‌شود، و قانون ۱ (یک hook برای هر key) این را هم حل می‌کند: یک hook یعنی یک type.

۳. cache در حافظه است.

  • چرخاندن گوشی مشکلی ندارد (در demo دیدیم): process زنده است، پس Singleton هم.
  • ولی وقتی اپ در background است و سیستم process را می‌بندد (process death)، با برگشتن کاربر همه‌ی جعبه‌ها خالی‌اند: اول Loading، بعد fetch.
  • راه‌حل: ComposeCleanArch یک tier ی دوم دارد: useCachedQuery که Room را منبع حقیقت می‌کند. data فوراً از دیتابیس می‌آید و پشت صحنه تازه می‌شود؛ offline هم کار می‌کند. جلسه‌ی ۳.

۴. hook فقط داخل Compose کار می‌کند.

  • useQuery از remember و DisposableEffect استفاده می‌کند، پس فقط در یک @Composable صدا زده می‌شود. یعنی گرفتن data به لایه‌ی UI نزدیک شده.
  • Worker، Service یا push notification hook ندارند. ولی QueryClient یک Singleton ی Hilt است: inject کنید و invalidate بزنید. مثال: push «سفارش شما انجام شد» → queryClient.invalidate(…) و هر screen ی باز خودش تازه می‌شود.
  • engine (QueryClient و QueryEntry) Kotlin خالص است و ۱۲ unit test دارد. test ی screen با Compose UI test و یک repository ی fake است؛ این‌ها هنوز در repo نیستند.

روی اسلاید، build به build

  1. «قبل از جمع‌بندی، صادق باشیم. هر طراحی هزینه‌ای دارد.»
  2. → اولین hook: «computeIfAbsent فقط بار اول جعبه را می‌سازد. پس برای هر key فقط یک hook.»
  3. → دو type: «map type را نگه نمی‌دارد. خطا در runtime است، نه compile. برای همین key فقط از XxxKeys.»
  4. → process death: «cache در حافظه است. برای offline، useCachedQuery با Room؛ جلسه‌ی ۳.»
  5. → فقط Compose: «از Worker یا push، QueryClient را inject کنید و invalidate بزنید.»

اسلاید ۳۰: سؤال

قانون: سؤال‌های «چرا» و «چه» را امروز جواب بدهید. سؤال‌های «کِی و چطور در engine» را یادداشت کنید و بگویید «جلسه‌ی بعد».

پیوست

پیوست — سؤال‌های احتمالی جلسه‌ی ۱

جواب کوتاه بدهید. اگر سؤال درباره‌ی جزئیات engine بود، بگویید «جلسه‌ی بعد» و یادداشتش کنید.

چرا خود TanStack Query را استفاده نکنیم؟ TanStack Query برای JavaScript است و نسخه‌ی Kotlin ندارد. ما ایده و شکل API را گرفتیم و در حدود ۸۸۰ خط Kotlin ساختیم.

چرا Store5 نه؟ Store5 cache را در لایه‌ی repository می‌گذارد و نمی‌داند کدام screen الان روی صفحه است؛ باز هم برای وصل کردنش به UI به ViewModel نیاز داریم. engine ما به lifecycle خود screen وصل است.

فرقش با shared ViewModel چیست؟ shared ViewModel یک state holder است که با owner و key پیدا می‌شود و عمرش به همان owner بسته است؛ cache و staleTime و refetch و invalidate را باید خودتان بنویسید. جعبه یک cache از server data است که با key پیدا می‌شود، بعد از رفتن screen هم تا cacheTime می‌ماند، و این قانون‌ها را از قبل دارد. جواب کامل در فصل ۹.

پس ViewModel را کنار بگذاریم؟ نه. ViewModel برای screen state می‌ماند: فرم‌ها، validation، جریان‌های چندمرحله‌ای. فقط گرفتن server data را از دوشش برمی‌داریم. جلسه‌ی ۳ دقیق.

باید کل اپ را منتقل کنیم؟ نه. ViewModel و hook کنار هم کار می‌کنند. یک بار QueryClient و ProvideQueryClient، بعد هر بار یک screen که فقط data می‌خواند. جواب کامل در فصل ۲۱.

با hiltViewModel در hook، باز ViewModel داریم؟ HookProvider یک HiltViewModel است فقط برای اینکه hookها به repositoryهای Hilt برسند. نه state دارد، نه fetch می‌کند.

با چرخش صفحه (configuration change) چه می‌شود؟ QueryClient یک Singleton است و زنده می‌ماند. screen دوباره ساخته می‌شود و همان جعبه را با همان key می‌گیرد؛ data همان‌جاست.

اگر key را اشتباه تایپ کنم؟ برای همین keyها فقط در یک object کنار Api ساخته می‌شوند (ArticleKeys.headlines(...))؛ هیچ رشته‌ی دستی در hook یا mutation نمی‌نویسیم.

این در production امتحان شده؟ بله. همین معماری در یک اپ معاملاتی رمزارز بیش از یک سال در production است: بیش از ۱۷۰ hook و چهار اپ white-label روی یک engine. ComposeCleanArch نسخه‌ی تمیز و تست‌شده‌ی آن است، با ۱۲ test برای engine. (اسم اپ را نگویید.)

هر recomposition یک request می‌زند؟ نه. جعبه با remember(key) یک بار گرفته می‌شود. request فقط در حالت‌های مشخص می‌رود؛ جلسه‌ی بعد.

اسلاید ۱۱ — React Query (JavaScript)

const { data, isLoading, error } = useQuery({
  queryKey: ['articles', source],
  queryFn: () => api.getHeadlines(source),
})
  • const { data, isLoading, error } = … یعنی سه فیلد را از نتیجه بیرون بکش؛ مثل val (a, b) = pair در Kotlin.
  • queryKey اسم data در cache است. اگر source عوض شود، key عوض می‌شود و data جدید گرفته می‌شود.
  • queryFn: () => … یک lambda است؛ مثل { api.getHeadlines(source) } در Kotlin.

اسلاید ۱۶ — key

// bug: page is not in the key
useQuery(key = "headlines") { repo.getHeadlines(source, page) }

// fix
useQuery(key = ArticleKeys.headlines(source, page)) { repo.getHeadlines(source, page) }
  • در نسخه‌ی اول همه‌ی صفحه‌ها یک key دارند، پس یک جعبه؛ صفحه‌ی ۲ همان data‌ی صفحه‌ی ۱ را نشان می‌دهد.
  • ArticleKeys.headlines(source, page) رشته‌ای مثل "articles.headlines.techcrunch.2" می‌سازد؛ هر صفحه جعبه‌ی خودش.

اسلاید ۱۸ — QueryClient (ساده‌شده)

@Singleton
class QueryClient {
  val entries = ConcurrentHashMap<String, QueryEntry>()
  fun getOrCreate(key: String) =
    entries.computeIfAbsent(key) { QueryEntry(key) }
}
  • ConcurrentHashMap چون از چند thread صدا زده می‌شود.
  • computeIfAbsent(key) { … } اگر key هست مقدارش را برمی‌گرداند؛ اگر نیست lambda را اجرا می‌کند، نتیجه را ذخیره و برمی‌گرداند. به‌صورت اتمی.
  • در کد واقعی getOrCreate fetcher، staleTime، cacheTime و چند پارامتر دیگر هم می‌گیرد.

اسلاید ۲۲ — hook (از ArticleHooks.kt)

@Composable
fun useHeadlines(source: String, page: Int = 1): QueryResult<List<Article>> {
    val provider = hiltViewModel<HookProvider>()
    return useQuery(
        key = ArticleKeys.headlines(source, page),
        fetcher = { provider.articleRepository.getHeadlines(source, page) },
    )
}

val headlines = useHeadlines("techcrunch")
QueryContent(headlines) { ArticleList(it) }
  • @Composable چون داخلش useQuery صدا زده می‌شود که از remember و DisposableEffect استفاده می‌کند.
  • QueryResult<List<Article>> شامل state، data، error، isLoading و تابع refetch است.
  • hiltViewModel<HookProvider>() راه رسیدن به repositoryهای Hilt از Compose.
  • fetcher یک lambda که data برمی‌گرداند یا exception پرتاب می‌کند؛ engine خودش آن را به AppError تبدیل می‌کند.
  • QueryContent(headlines) { ArticleList(it) }: it همان data است، فقط وقتی حالت Success است.

اسلاید ۲۳ — QueryState

sealed interface QueryState<out T> {
    data object Loading : QueryState<Nothing>
    data class Success<out T>(val data: T, val refreshing: Boolean = false) : QueryState<T>
    data class Failure(val error: AppError) : QueryState<Nothing>
}
  • sealed: همه‌ی زیرنوع‌ها همین‌جا؛ when کامل است بدون else.
  • Nothing زیرنوع همه‌چیز است و out T اجازه می‌دهد Loading جای QueryState<List<Article>> هم قبول شود.
  • refreshing = true: data قبلی روی صفحه، refetch پشت صحنه.

اسلاید ۲۴ — useMutation

val buy = useMutation<BuyRequest, Order>(
    mutationFn = { req -> repo.buy(req) },
    options = MutationOptions(invalidateKeys = listOf(WalletKeys.balance("USDT"))),

Button(onClick = { buy(request) }) { Text("Buy") }
  • دو نوع generic: ورودی (BuyRequest) و خروجی (Order).
  • invalidateKeys: بعد از موفقیت این جعبه‌ها کهنه علامت می‌خورند و screenهایی که نگاهشان می‌کنند refetch می‌شوند.
  • buy(request): نتیجه‌ی useMutation یک operator fun invoke دارد، پس مثل تابع صدا زده می‌شود.
